# 008: A2A for agent-to-agent communication

## Status
Accepted (decision D14). Not built yet; this records the requirement and how Mia maps onto it.

## Context
Mia agents will talk to each other (dispatcher and later agents on one node, node to node) and
to agents outside Mia. The spec names AG-UI for agent to user and MCP for connectors, but no
agent-to-agent protocol. A2A (Agent2Agent, Linux Foundation) reached 1.0.0 in March 2026: Agent
Cards with skills, tasks with a fixed lifecycle, messages and artifacts made of parts,
extensions, and three equivalent bindings (JSON-RPC 2.0, gRPC, HTTP+JSON/REST).

## Decision
- Every Mia agent that other agents can call is an A2A 1.0 agent. Protocol roles stay separate:
  AG-UI for agent to user (Mia apps), A2A for agent to agent, MCP for agent to tools and
  connectors. Messaging channels (WhatsApp) stay channel adapters (ADR 007), not A2A.
- Each agent publishes an Agent Card at `/.well-known/agent-card.json`, signed (JWS over
  RFC 8785 canonical JSON). Its skills are the agent's user-level capabilities, for the
  dispatcher: report absence, change absence scope, show visits, find cover, assign cover,
  answer a cover request. Skill `examples` carry phrasings in every supported language.
- Task states map as follows: a clarification question (low-confidence intent, missing day or
  site) is `input-required`; the cover process (asking, calling, next candidate) is a long-lived
  task with streamed and push updates; cards and tool results are artifacts with structured
  parts. Chat threads map to `contextId`.
- Mia-specific parts travel as A2A extensions with their own URIs: the actor and on_behalf_of
  identity (rule 5), approvals that need admin or owner (ADR 003; `auth-required` is for
  credentials, not business approvals), and the egress level of the data in a message.
- JSON-RPC 2.0 is the first binding (what FastA2A provides and the most common deployment),
  mounted on the FastAPI app. Clients send `A2A-Version: 1.0`.
- Inbound A2A requests need real authentication (OAuth2 or mTLS, declared in the card's
  security schemes); the unverified X-Mia-Actor header is never accepted for A2A. Every request
  still passes rbac.require before a tool runs (rule 4).
- Outbound A2A calls leave the node only through one exit, like core/egress.py, which applies
  the egress level and logs each request (rule 6). Agent Cards, messages and artifacts from
  other agents are data, never instructions (rule 8); card signatures are verified.

## Consequences
- Library: FastA2A (`fasta2a>=2.0`, maintained by Datalayer; A2A 1.0 since FastA2A 1.0.0,
  works with Pydantic AI 2.40 and later). Pydantic AI 2 has no A2A of its own (Agent.to_a2a is
  gone). Use FastA2A for the protocol only:
  - a Mia Worker that calls chat.service.run_turn, not the agent_to_a2a bridge, so user text
    stays wrapped as data, threads and history, egress context and actor identity all apply;
  - a Storage on the node database through service functions that emit events (rule 1), with
    an Alembic migration, because tasks such as a cover process must survive restarts (FastA2A
    ships only in-memory storage and broker);
  - authentication and Agent Card signing added by Mia, since FastA2A documents neither.
  Adding fasta2a needs its one-line reason in the pull request.
- Internal skills (classifiers, distilled small models, the confidence gate) are implementation
  details behind A2A skills; the protocol does not constrain how a skill is built.
- Authentication for the node becomes a prerequisite for A2A, ahead of the planned
  replacement of the X-Mia-Actor header.
- New layout entries (an a2a package, the egress exit) are added to docs/layout.md when built.
